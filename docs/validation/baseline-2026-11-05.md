## Verification harness (Task 0.2–0.4) — validated on Lesson 1

The harness (`scripts/verification/`) builds a model from a per-lesson
`build.py`, solves it through the CLI with a wall-clock cap, extracts the
compared quantity, applies the plan's pass metric, and writes
`docs/validation/plaxis-parity-report.md`. Confirmed working end to end on L1:

| Case | Quantity | KATAI | Reference | Error | Verdict |
|---|---|---|---|---|---|
| KV-PLX-L01-B | flexible footing capacity q·πR² [kN] | 590.6 | 590 | 0.10 % | **PASS** |
| KV-PLX-L01-A | rigid footing reaction Force-Y·2π [kN] | 656.3 | 588 | 11.62 % | **FAIL** (mesh) |

### L1-A finding: rigid-footing reaction is mesh-sensitive

The rigid-footing reaction over-predicts on a coarse mesh because of the stress
singularity at the footing edge. A refinement study (axisymmetric, 15-noded)
shows monotone convergence toward the PLAXIS value:

| elem_size [m] | elements | Force-Y [kN] | error vs 588 | solve time |
|---|---|---|---|---|
| 1.00 | 62 | 656.3 | +11.62 % | 0.9 s |
| 0.50 | 255 | 625.6 | +6.39 % | 7.2 s |
| 0.25 | 959 | 605.2 | +2.92 % | 556.8 s |
| 0.15 | — | — | — | > 300 s (did not finish in budget) |

Two conclusions for later phases:

1. **The model is right; the discretisation is the error.** The sequence is
   monotone toward 588 kN. This is the expected behaviour of a rigid indentation
   on an axisymmetric mesh (documented for PLAXIS too). Phase 6 will pin L1-A
   with a mesh whose element count matches what PLAXIS 'Medium' produces for
   this geometry, and state the residual as a measured discretisation bias
   rather than chasing it with parameter changes.
2. **This is a Phase 11 performance case.** elem_size 0.25 takes ~557 s and 0.15
   does not finish in 300 s — matching CHANGELOG notes that a footing on a fine
   mesh is very slow. The L1-A refinement is the first entry in the performance
   log: getting below the 2 % band and under the 5-minute cap at the same time
   needs the step-control / tolerance investigation (tolerated error: KATAI runs
   Mohr-Coulomb at 1e-6, PLAXIS at 0.01).

## Pre-existing failures on branch `modifikasi` (NOT introduced by this work)

The branch does **not** start fully green. Before any PLAXIS-parity change, the
fast source/spec gates were run and one fails:

- **`check_k2d_spec` — FAIL (21 problems), pre-existing.** The `.k2d`/`.res`
  spec gate reports that the mesh fields the writer emits inside `explicit_mesh`
  (`node_count`, `element_count`, `nodes_per_element`, `connectivity`,
  `element_material`, `boundary_nodes`) and `explicit_mesh` itself are absent
  from `docs/k2d-format.md` and `docs/k2d.schema.json` and are never read back,
  and that `docs/k2d-format.md` records `.res` version 11 while the code's
  `kResultsFileVersion` is 12. These live in `kernel/io/.../project_io.hpp`,
  `docs/k2d-format.md` and `docs/k2d.schema.json` — none touched by this work
  (the only tracked change here is one additive ctest entry in
  `tests/CMakeLists.txt`). Verified with `git status`: everything else added is
  untracked under `scripts/verification/`, `tests/verification/`, `docs/`.

  This matters for the plan: Phase 3/4 touch the schema and will have to bring
  these mesh fields and the `.res` version into the spec docs, at which point
  this gate should be made to pass. It is logged here so a later green
  `check_k2d_spec` is a fix we made, not a surprise.

- `check_language`, `check_architecture`, `test_reference_registry`,
  `check_silent_drop` — **PASS**.
- `plaxis_harness_smoke` (new) — **PASS** (3.76 s).

### Web test drift on branch `modifikasi` (pre-existing, found during Phase 1)

The committed web tests were written against an older UI/server and do not match
the current code. This is independent of the PLAXIS-parity work and was the
state at the start of Phase 1:

- **`web/server/test_app.py` — pre-existing FAIL.** The tests monkeypatch
  `app.TOKEN`, but `app.py` uses `TOKENS` (a list from `KATAI_ACCESS_TOKEN`).
  So `monkeypatch.setattr(service, "TOKEN", ...)` raises `AttributeError`
  regardless of inputs. Verified the fixture relocation itself is fine (the
  moved `tutorial1-*.k2d` load without error; the failure is the TOKEN attr).
- **`web/client/e2e/*.spec.ts` (old) — pre-existing FAIL.** `tutorial.spec.ts`
  and `corpus.spec.ts` referenced CAD-toolbar titles from a previous UI
  (`'Soil polygon'`, `'Structure line'`, …) that no longer exist; the current
  toolbar uses `'Toolbar: Soil Region'`, `'Toolbar: Plate Structure'`, etc.
- **`web/client/tests/*.spec.ts` — a separate, older suite** on port 5174 with
  absolute external screenshot paths; not run by the default Playwright config
  (`testDir: './e2e'`).

Phase 1 adds a clean, passing canvas safety net (`e2e/canvas.spec.ts`, 2 tests)
and realigns `corpus.spec.ts` tool titles. Repairing the rest of the stale web
suite (incl. the server TOKEN drift) is folded into Phases 2–5, which rewrite
the server auth surface and the Input/Output shells those specs target.
